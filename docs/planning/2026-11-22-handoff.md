## 1. The project

- **Name:** Co-Hendrix (earlier working name: Muse-MIDI).
- **One line:** a verified AI tool that generates and edits multi-track MIDI within the rules the producer sets.
- **Core idea:** generation is left to an untrusted cloud LLM; verification is done by deterministic code. The producer locks one region (tracks × bars) per request; the LLM proposes exactly one patch; the code checks that nothing outside the region changed and that every confirmed rule (key, pitch range, rhythm grid) holds; up to 3 repairs; otherwise abstain. Export is a standard `.mid` file opened in the producer's own DAW.
- **Guaranteed:** confirmed rules hold, protected bars stay untouched. **Measured, not promised:** musical quality, originality, fit to the producer's taste.
- **Course:** BGU "Project in Software Engineering" (373.1.4401 / 373.1.4402), team of 4.
- **Team:** Oren Kashani, Stav Ronen, Daniel Blanga, Eden Sabika.
- **Academic advisor:** Dr. Avi Segal.
- **Customer:** DJ LIRANO (Liron Goldvaser), producer and DJ.

The full requirements are in the ARD ([`docs/requirements/ard.md`](../requirements/ard.md), revised 15 Nov 2026; its decisions are recorded in ADRs 0002–0012). Requirement IDs used everywhere: FR1–FR26, NFR1–NFR17, risks R1–R7, upgrades EXT1–EXT4, Alpha constraints C1–C4.

## 3. Decisions log

**Documents and presentations**

- The ARD and all slides are in English; presentations are spoken in Hebrew.
- Positioning line: "AI MIDI edits you can trust". The system *extracts features* and suggests rules ("taste as rules"); never say it "learns your taste".
- Closest competitors (public docs, Nov 2026): Suno Studio 2.0, MIDI Agent, Staccato, Logic Session Players. Our edge: protected bars, rules checked in code, a blocked patch is never applied. Hands-on testing is planned for Sprint 1.
- Context diagram: Co-Hendrix as one block; solid lines = direct interfaces (producer, LLM), dashed lines = files the producer moves by hand (DAW, reference library). The producer gets back "the edited result, or why it failed".
- Final requirements-review deck: `Co-Hendrix_Requirements_Review.pptx`. In it, the LLM box on slide 5 is labelled "AI Model", and the advisor appears only on the cover slide. When editing that deck: keep the original design and change only what is asked.

**Development method (chosen 22 Nov 2026: method C)**

- Phase 1, now → hackathon: the whole team builds one thin end-to-end slice (the Alpha, ARD 5.2: one real file, constraint C1, one real LLM, every module). Each member builds one layer. Score and Patch schemas are frozen first.
- Phase 2, after the hackathon → June: each member owns one functional area end to end (UI, logic, tests, maintenance) and stewards one shared component. Proposed areas: Verification and repair · Rules and sketch input · Region, review and export · Windows, models and run records (details in [`development-plan.md`](development-plan.md)).
- Rejected alternatives: pure feature ownership from day one (integration risk R6, uneven load, knowledge silos); pure component ownership (late integration, nobody owns user value).
- Team rules: definition of done; every PR reviewed by a non-owner; schema changes need all four stewards; AI-assisted code allowed only if the author can explain every line, with tests.
- Tasks are tracked on a GitHub Projects Kanban board.
